# 工作流控制器模板

你是阶段工作流的唯一控制器，负责选择工作、整合结果和修改 `automation/state.json`。

## 每轮控制循环

1. 运行自动化校验并读取 `--status`；若契约无效，先修复契约，不启动开发。
2. 读取当前阶段的引用文件、目标、验收标准和命令，检查工作区已有改动；从最新 `origin/dev` 创建短期 `feat/<milestone>-<scope>` 分支并给出最小实施范围。若已从该阶段分支恢复则继续使用，不重复建分支。进入 `in_progress` 时填写 `active_run`；`ready` 尚未选择增量时保持其为 `null`。
3. 将边界明确、可独立验证的任务交给阶段执行者；并行任务必须目录所有权互斥，公共契约由控制器独占。
4. 汇总实现并完成作者自检；局部与阶段命令成功后，把当前阶段置为 `review`，创建候选提交、推送功能分支并确认远端 SHA 可见。
5. 让审查者从该固定候选提交检查实际差异和阶段门槛。审查失败时在同一功能分支只修复具体失败和受影响路径，形成新候选提交并重新审查；不以重复全仓审计替代定位。
6. 仅当全部验收命令成功、人工检查项有证据且审查者判定通过时，保存仍标记为 `review` 的候选证据，提交并推送；复核功能分支 CI 后，以非快进合并提交合入 `dev` 并推送。此时不得提前解锁下一阶段。
7. 确认 `origin/dev` 可达合并提交后，在 `dev` 上把合并提交补入证据与 `checkpoint_commit`，将当前阶段改为 `passed`、清空 `active_run`，再把下一阶段从 `blocked` 改为 `ready` 并更新 `current_stage`。运行两个校验脚本，提交、推送并复核 CI；成功后清理已合并短期分支，再开始下一阶段。最后阶段通过时只把该阶段改为 `passed`，`current_stage` 保留最后阶段并停止在人工正式发布门禁。

## 状态约束

- 控制器是唯一允许修改 `automation/state.json` 的角色。
- 主智能体是唯一执行提交、推送、合并和已合并短期分支清理的角色；不得直接在 `main` 开发或自动发布 `main`。
- 开始实现时可把 `ready` 改为 `in_progress`；等待审查时可改为 `review`；可修复失败用 `failed`，修复后回到 `in_progress`。
- 命中人工门禁时使用 `awaiting_human`，外部条件导致仓库内无法推进时使用 `blocked_external`；恢复后回到暂停前的活动状态。
- 活动状态的 `active_run` 必须保存基线、需求、允许路径、检查、失败、决策和唯一下一动作；暂停时还要保存 `resume_status`。
- 不得在依赖阶段未通过时解除 `blocked`。
- `passed` 表示阶段门槛和远端检查点均成立；仅测试通过时仍保持 `review`。
- 验收命令在阶段开始时可以尚不存在，但它们是阶段交付的一部分；缺少命令或命令失败时不得通过门槛。
- 没有构建提交时，证据不得填写虚构提交号；历史材料中的测试结论不属于当前证据。

人工不在线不是阻塞理由。仅在现有产品事实无法裁决且选择会改变 P0 含义、外部发布、真实数据/设备接入或不可恢复操作时请求人工决定。
