# 版本与标签策略

## 版本语义

- `v0.1.0`：M0–M7 可运行功能基线，已通过 PR #1 合入 `main`。
- `v0.2.0`：M9 可泛化算法模型通过后的功能标签。
- `v0.5.0`：M10 项目化业务与全中文 UX 通过后的功能标签。
- `v0.8.0`：M12 安全部署、恢复和可靠性通过后的可部署标签。
- `v1.0.0`：M14 自动验收通过、项目负责人确认交付可行并授权正式发布、发布 PR 合入 `main` 且远端 CI 通过后的正式版本标签。

## 标签门槛

标签使用 annotated tag，并且只能指向满足以下条件的 `main` 提交：

1. 功能阶段已形成经过验收的 `dev` 非快进合并检查点；
2. 发布 PR 已把该检查点合入 `main`，且合并树与受审候选一致；
3. `main` 合并提交的阶段命令、适用远端 CI 和发布冒烟全部成功；
4. 证据文件记录候选、合并提交的完整 SHA 和结果；
5. 工作树干净，远端 `main` 与 `dev` 均精确可达该发布结果；
6. 标签名称尚不存在。

M9、M10、M12 和 M14 的版本号表示可发布功能里程碑，因此也必须先走 `dev → main` 发布 PR；普通阶段检查点只保留提交和证据，不另打 Git 标签。不在文档提交、失败候选、`dev` 单边提交、PR 临时合并引用或未核验工作树上打标签。标签不是替代测试的进度标记。

M14 使用四个失败关闭的校验模式：`candidate` 只允许 SC-042 仍归 M14 且人工记录为空；项目负责人保存结果性验收声明、固定候选和已验证 ZIP 摘要后，关闭两份矩阵并进入 `approved`；发布 PR 合入 main、main 结果同步回 dev 后创建 annotated `v1.0.0`，标签事件运行 `post-main`；最终证据同步回 dev、M14 标记 passed 后运行 `released`。后三种模式要求结构化项目负责人声明、正式发布授权和无悬空阶段责任。

人工确认后只允许修改说明书、项目报告、专利草案、发布治理、版本元数据及对应生成物；允许集合由发布校验器逐路径冻结。业务源码、数据库迁移、算法实现、样例或用户可见流程发生变化时，必须重建候选并重新执行相应运行验收。项目负责人没有提供的姓名、设备版本、逐项结果或签名不得由自动化推断补写。
