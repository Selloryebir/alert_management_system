## 实现范围

M11 在既有 Java 单体边界内实现同源有状态会话，不引入 JWT、独立网关或通用权限平台：

- 口令使用 BCrypt 保存；首次启动只生成一次管理员口令文件，登录、退出、会话过期和 CSRF 保护形成闭环。
- `SYSTEM_ADMIN` 为全局角色，`MANAGER`、`ANALYST` 为项目成员角色；项目读取、导入、分析、处置、报告、审计和复位均按职责授权。
- 审计操作者来自认证上下文，不接受客户端伪造；前端提供中文登录、无权限、会话失效和成员管理反馈。
- 上传大小、行列数、单元格长度、请求体和查询参数均有可验证上限，错误使用稳定中文反馈。
- Windows 本机模式仅监听回环 HTTP；网络模式仅公开 HTTPS 8443，HTTP 8080、PostgreSQL 和算法服务不对局域网暴露。缺失 TLS 材料时拒绝启动。
- Windows Compose 密钥目录设置为当前用户专用 ACL；临时口令、数据库口令、会话和证书私钥不进入仓库或证据正文。
- 数据库只新增 Flyway V9 身份与项目成员迁移，未修改 V1–V8 历史迁移。

## 并发事务缺陷闭环

演示复位、分析完成和分析失败会同时改写多张业务表。仅统一表锁顺序仍会与分析持久化路径形成反向等待，因此最终实现增加固定 PostgreSQL 事务级 advisory lock：

- `begin`、`complete`、`fail` 和 `reset` 均在接触业务表前获取同一事务门闩。
- 算法服务 HTTP 调用保持在门闩之外，不延长数据库临界区。
- 项目统计仍保持父表到子表的读取顺序。
- 两个嵌入式真实 PostgreSQL 并发测试分别由独立 JDBC 事务持有门闩，验证应用 Future 未提前完成、`pg_locks` 存在未授予等待者，释放后再校验成功结果。

目标并发集成测试 16/16 通过。独立复审检查了导入、项目、人工报警、处置、分类修订和报告路径，未发现仍可达的反向锁循环。

## 独立审查与缺陷闭环

独立审查者未参与主实现提交，并在最终固定候选给出 PASS。开发中发现的问题均由失败门槛驱动最小修正：

1. 初始启动与证据路径可能暴露引导口令，已改为受限文件和脱敏输出。
2. Windows Compose 密钥目录原先只依赖文件属性，已增加当前用户专用 ACL 并在标准用户流水线验证。
3. 旧 M2–M5 浏览器验收未登录，已改为真实认证、CSRF 和职责路径，不保留测试绕过。
4. Docker Desktop 瞬时状态探测会造成假失败，已改为有界重试，不无限等待。
5. 第一版复位锁顺序仍与分析完成/失败存在死锁环，独立审查判定 FAIL；固定事务门闩和真实并发屏障测试完成后复审通过。

失败候选不作为通过依据；Maven 下载 403 也保留在 run 尝试历史中。最终通过只绑定固定候选的完整成功尝试、黑盒安全检查和独立复审。
