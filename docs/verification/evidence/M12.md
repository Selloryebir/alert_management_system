## 实现范围

M12 沿用现有 Java 单体、Python 算法服务和 PostgreSQL 数据边界，不引入第二套部署或运维平台：

- Windows 原生包生成 PostgreSQL 自定义格式恢复点及配套元数据；状态检查验证大小和 SHA-256，计划任务、保留策略和管理员只读容量/恢复点页面形成运营闭环。
- `restore-verify.ps1` 在系统临时目录的当前实例专属短路径中启动隔离 PostgreSQL，用 `pg_restore --exit-on-error` 真正恢复，再核验 Flyway、关键表、稳定内容摘要和序列。它不停止、覆盖或写入业务数据库。
- 安装、停止、备份、隔离恢复和清理共用实例身份与互斥边界；清理拒绝未知实例、路径越界、reparse 目录、锁冲突和未知进程，默认保留恢复点。
- 质量入口检查 UTF-8、行尾、JSON/TOML、Bash/PowerShell 语法、Java/Python/Vue 构建、锁文件，以及 Maven、PyPI、npm 三类实际依赖的已知漏洞；网络或审计器失败不会记作通过。
- 有限可靠性入口重复真实导入、分析、看板和复位，采集受管进程 RSS、后端 Full GC 后活对象、TCP 连接、服务日志、乱码、秘密、端口和 PID 清理结果，不复制或模拟业务结果。
- 开发、Windows 原生和 Docker 四类后端启动入口统一使用 `-Xms128m -Xmx768m`，避免 JVM 按宿主总内存扩大堆，同时保留 20,000 行演示所需空间。

## 独立审查与缺陷闭环

独立审查者未参与主实现提交。其对 `f210619` 的实现以及本证据、状态与工作流 diff 的最终复核均为 PASS：缺少 `jcmd`、PID 不存在、Windows 命令非零、空或畸形直方图、缺失 live 字段、持续增长和 RSS 超限等定向负控均实际拒绝；固定候选、历史失败和证据提交检查的 SHA 边界也已明确区分。开发中由真实门槛触发并闭合的问题包括：

1. 恢复脚本的 PowerShell 字段别名、布尔文本和进程启动等待曾使恢复验收失败，现由真实隔离恢复和 17 项逐表事实锁定。
2. 发布目录叠加恢复目录曾达到 Windows 260 字符边界，现把隔离集群放到带实例/本轮身份标记的短 TEMP 路径；删除前核验 marker、identity、reparse 和边界。
3. 初版 WSL 桥重试范围过宽，现只重试已知 Maven 下载瞬断或 Windows 观测通道故障；应用、进程和命令真实失败不重试。
4. JVM 预热被五个小样本误判为泄漏，现小样本只执行硬上限，持续趋势由三轮 20,000 行重载判断；随后真实重载暴露默认 JVM 堆扩张，四类启动入口统一限定 128–768 MiB。
5. PostgreSQL 官方镜像初始化的受控 fast shutdown 被日志规则误报，现只在同一 FATAL 前 20 行存在 `received fast shutdown request`、后 30 行存在 `database system is shut down` 时过滤该精确行；其他 ERROR/FATAL/PANIC 仍阻断。
6. WSL/Windows 观测瞬断曾把健康后端记作内存不可读，最终逻辑用显式 `RSS:`、`OK`、`MISSING` 标记区分通道故障与进程退出，并经正负控和完整串行重跑证明。
7. 候选 `7add6f8` 通过后经 PR #10 合入 `dev`，但合并提交 `a4d4b15` 的后端原始 RSS 为 655.113→741.578→832.949 MiB，触发旧趋势门槛，因此该检查点保留为失败且 M12 未通过。同一实现树在本机及先前远端出现相互矛盾的 RSS 轨迹，证明 JVM 已提交内存受 GC/JIT 时机影响；当前候选改用 Full GC 后活对象趋势，同时保留 RSS 硬上限。
8. Windows/WSL 挂载盘上的 Vitest 线程 worker 曾在已通过 3 个文件、22 项后等待 worker 超时；最终只把测试池改为单 worker `forks`，35 项测试范围与断言不变，避免以删除测试或增加并发掩盖基础设施问题。

失败候选和失败结果目录不作为通过依据；最终结论只绑定 `f210619` 的三条本机 G12 与四条远端功能检查、证据提交上的仓库检查和独立复审。
