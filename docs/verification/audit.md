# 业务审计与开发证据策略

## 1. 目的与边界

业务审计用于回答“谁在何时对哪个批次/分析/处置做了什么，结果如何”，支持审核演示和问题复盘。它不是防恶意篡改系统，本阶段不引入区块链、签名链或无实际收益的哈希仪式。

开发证据用于回答“哪个提交在什么环境通过了哪些检查”。两者分开保存，历史材料的结论不能替代任一类当前证据。

## 2. 必须记录的业务事件

| 事件类型 | 触发点 | 必要结果字段 |
|---|---|---|
| `IMPORT_CREATED` | 文件被接收 | 文件名、格式、批次、记录数 |
| `IMPORT_REJECTED` | 全量校验失败 | 批次、错误计数、主要错误码 |
| `IMPORT_CONFIRMED` | 用户确认并完成落库 | 批次、成功数、警告数 |
| `ANALYSIS_STARTED` | Java 发起分析 | 批次、运行标识、算法/契约版本 |
| `ANALYSIS_COMPLETED` | 结果完整保存 | 运行标识、输入/输出计数、摘要 |
| `ANALYSIS_FAILED` | 调用或契约校验失败 | 运行标识、稳定错误码、可重试性 |
| `RESULT_OVERRIDDEN` | 人工修订分类/结论 | 记录、原值、新值、理由 |
| `DISPOSITION_CHANGED` | 处置状态变更 | 对象、前后状态、处置说明 |
| `REPORT_EXPORTED` | 报告成功生成 | 报告类型、筛选条件、记录数 |

每条事件共同字段：事件 UUID、事件类型、发生时间、操作者、目标类型/标识、结果（成功/失败）、`trace_id`、结构化详情。详情不得保存整份源文件或用户不需要的敏感内容。

本地演示若未实现多用户认证，操作者使用发布配置中明确显示的 `demo-reviewer`，页面同时标注“本地演示身份”；不得伪造成历史真实人员。

## 3. 行为规则

- 审计写入与对应业务数据库变更处于同一 Java 事务；外部算法失败事件在 Java 确认失败后记录。
- 审计记录通过只读 API/页面查询，业务页面不提供逐条修改或删除。
- `reset-demo` 可以清空本地演示审计并重新播种，执行前明确展示目标数据目录；这属于演示复位，不伪装为业务删除。
- 报告生成失败不记录 `REPORT_EXPORTED` 成功事件，应记录应用错误并向用户返回失败。
- 当前阶段只需满足演示周期留存，不承诺法规或生产环境保留期限。

## 4. 开发与验收证据

每个阶段证据至少包括：

- 里程碑和对应 `PRD-*`；
- Git 提交 ID及工作区是否干净；
- 执行平台和发布包版本；
- 实际命令、退出码和关键摘要；
- 测试数据种子、生成器和算法版本；
- 失败项、修复提交和复测范围；
- 门槛通过/不通过结论及判定人。

证据跟随阶段提交推送到远端；大日志保留在发布产物旁并在证据中给出相对位置。不得粘贴未经运行的预期输出冒充结果，也不得因接近审核日期删除失败证据。
