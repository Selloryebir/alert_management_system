# 自动化开发与阶段证据审计指南

## 1. 审计目标

本指南用于判断智能体开发产生的“阶段已通过”结论是否由当前提交上的真实证据支持。业务运行时审计字段见[业务审计与开发证据策略](./audit.md)，测试层次、P0 用例和缺陷等级的权威定义见[测试与阶段验收策略](./README.md)，阶段步骤及 G0–G7 门槛见[阶段开发计划](../planning/README.md)。本文只补充证据采集、独立复核和放行规则。

审计对象是一个固定候选：被测提交、运行平台、配置、样例版本和构建产物必须能相互对应。工作区继续变化后，旧结果不能自动证明新提交通过。

## 2. 每阶段证据包

每个候选只建立一份证据记录；失败、修复和复测追加在同一记录或使用明确的替代关系关联，不能删除原失败。记录至少包含：

- 里程碑、门槛、关联 `PRD-*` 和 `AC-*`；
- 被测提交 SHA、基线 SHA、分支、远端 SHA 核验结果和工作区状态；
- 操作系统、关键运行时版本、配置档位、样例种子和算法/生成器版本；
- 实际执行命令、开始/结束时间、退出码、关键结果摘要及原始日志相对位置；
- 失败项、缺陷编号、修复提交、复测命令和受影响回归范围；
- 作者自检结论、独立复核人/智能体、复核结论以及是否触发人工门禁；
- 最终状态：`通过`、`不通过` 或 `等待人工裁决`，不得使用含糊的“基本通过”。

证据文件可保存在 `docs/verification/evidence/<milestone>/`，但只有实际执行后才创建；不预填成功记录。大日志和发布构件不重复提交进 Git，按[既有证据策略](./audit.md#4-开发与验收证据)保存并记录可访问的相对位置。

## 3. G0–G7 最小证据

下表只规定每个门槛必须留下的证据类型，完整判定仍引用阶段计划，不在此改写验收步骤。

| 门槛 | 必留证据 | 独立复核重点 |
| --- | --- | --- |
| G0 | 来源清单、需求追踪/冲突状态、文档链接检查命令与结果 | 抽查来源页码或章节去向；确认未裁决项未进入 P0 |
| G1 | 干净检出构建记录、四组件启动与健康结果、数据库首次及重复迁移结果 | 从说明独立启动，确认无隐藏手工步骤和假健康 |
| G2 | CSV/TXT/XLSX 等价摘要、非法样例错误清单、事务前后数据量、20,000 行导入记录 | 独立查询三格式结果；确认失败批次没有半落库 |
| G3 | 固定种子重复运行结果、规则/契约版本、黄金测试、算法不可用及非法响应记录 | 使用测试组独立预期；确认失败不保存部分结果且无因果/真实准确率误述 |
| G4 | P0 浏览器 E2E、关键看板抽样对账、处置前后状态与审计记录、前端控制台结果 | 从浏览器重走主路径，并用独立 API/数据库查询复核数字 |
| G5 | PDF/XLSX 可打开记录及数字对账、关键审计事件、两次复位前后摘要 | 确认报告和界面同源；复位目标限定在 Demo 数据目录 |
| G6 | Windows 发布包标识、构建提交、预检/启停日志、新解压目录两轮彩排、未关闭缺陷清单 | 仅使用发布包，确认不依赖开发机 JDK/Python/Node 或绝对路径 |
| G7 | 空项目卷启动日志、复用的关键冒烟结果、与原生固定样例摘要对比 | 从空卷复现；确认没有第二套业务逻辑或迁移 |

某阶段不涉及的字段写明“不适用”及理由，不得空白后默认通过。上游门槛证据仍适用于同一提交时可以引用，不重复制造相同日志；只要代码、契约、迁移、样例或构建输入改变，就必须重新判断受影响证据。

## 4. 独立复核

1. 作者或开发子智能体先提交自检证据，但不能独自给阶段放行。
2. 测试组或未参与该变更的复核智能体从已推送的固定提交、干净工作树或发布构件执行复核，不使用作者仍在变化的工作区。
3. 复核者自行读取需求、契约和门槛，选择能发现关键失败的检查；不得只复述作者输出，也不得让待测实现生成自己的正确答案。
4. 复核结果写明实际命令、退出码、观察值和差异。发现问题后创建缺陷，作者修复；复核者在新提交上执行针对性复测。
5. 因并发限制只能由同一智能体复跑时，必须明确记录“非独立复核”，不得标记独立门槛已满足；可以继续不依赖该门槛的工作，但不能据此发布。

主智能体负责核对所有权交叉、候选 SHA 和证据完整性，不能通过改写测试预期、隐藏日志或降低缺陷等级来代替复核。子智能体的口头完成报告不是阶段证据。

## 5. 缺陷记录与分级审计

缺陷等级严格引用[权威分级及发布处理规则](./README.md#5-缺陷等级与发布门槛)，不得另设近义等级规避门槛。每个缺陷至少记录：编号、发现提交/构件、复现条件、预期与实际、日志或截图位置、等级、影响门槛、责任组、修复提交、复测证据和状态。

- `阻断`、`严重`：对应门槛立即判为不通过，修复并完成针对性复测前不得合入发布线。
- `一般`：必须记录可执行绕行、审核影响和处置决定；不能仅因日期临近降级。
- `建议`：不得伪装成当前必做项扩大范围，应回到规划决策。
- 等级升降必须写明新证据和复核者；作者不能单方面把阻断/严重问题降级后放行。
- 状态只按 `打开 → 已修复待复测 → 复测通过/重新打开 → 关闭` 流转。“提交了修复”不等于“关闭”。

修复后的回归范围按[既有策略](./README.md#5-缺陷等级与发布门槛)确定；没有证据表明受影响的模块不做仪式性全仓复测。

## 6. 人工门禁

普通实现选择、功能分支合入 `dev` 及已冻结契约内的缺陷修复，由主智能体依据证据自动推进，不等待人工。出现[产品事实层列出的人工介入事项](../product/README.md#6-何时必须人工介入)时，候选状态改为 `等待人工裁决`，记录问题、选项、影响和现有证据，在收到明确决定前不得把任何选项写成既定事实。

以下审计动作也必须人工确认：

- 接受未关闭的阻断/严重缺陷或跳过 P0 门槛；
- 将 `dev` 候选作为审核交付物合入/发布到 `main`；
- 强制推送、删除未合并远端分支、改写已共享历史等不可恢复 Git 操作；
- 对外发布报告、构件或合规/性能结论。

人工确认必须记录决定内容、适用候选 SHA、时间和影响范围；“用户曾授权自动开发”不能替代针对上述事项的明确决定。普通字段、页面布局和可逆内部实现不得借人工门禁拖延。

## 7. 禁止伪造或夸大证据

- 未运行写 `未运行`，失败写 `失败`；不得复制预期输出、旧提交结果、历史材料结论或其他平台日志冒充当前结果。
- 命令退出码、失败行和关键警告必须保留上下文；不得只摘取绿色片段、修改日志文字或用截图代替机器结果。
- 不得虚构提交 SHA、CI 任务、测试人数、真实 DCS 数据、现场试点、运行时长、准确率、性能或合规结论。
- 合成数据结果只能使用产品基线规定的口径；不得外推为真实工业准确率、千万级能力或 7×24 小时稳定性。
- 测试预期必须独立于待测算法；为使测试通过而同步修改实现与正确答案时，必须先有需求/契约依据并由独立复核者审查。
- 截图、演示视频和人工观察是辅助证据，不能替代退出码、API/数据库对账或发布包复现。
- 证据发现错误时追加更正并引用被替代记录，不静默删除失败。无法复现或丢失原始日志时，结论降为未验证并重新执行。

阶段通过只能表示对应门槛在固定候选上有充分证据，不等于“没有任何 bug”，也不扩大[当前发布口径](./README.md#1-验证目标)。
