# 测试与阶段验收策略

## 1. 验证目标

验证集中在审核人员实际可达的主流程及其直接失败路径。检查必须能发现一个具体问题并影响下一步行动；不进行无目标的全仓库审计，也不以测试数量替代闭环证据。

“无明显 bug”的发布口径定义为：P0 自动验收全部通过，两次 Windows 发布包彩排通过，当前未关闭的阻断/严重缺陷为零。该表述不保证不存在所有缺陷。

## 2. 测试层次

| 层次 | 所有者 | 主要检测问题 | 触发时机 |
|---|---|---|---|
| 单元测试 | 各开发组 | 解析边界、状态转换、规则命中、统计和报告映射错误 | 相关模块每次改动 |
| 数据黄金测试 | 算法组+测试组 | 规则输出偏离独立场景预期、结果不确定 | 算法或生成器改动 |
| 契约测试 | 后端组+算法组+前端组 | Java/Python 和前后端字段、枚举、错误结构漂移 | 公共契约或消费者改动 |
| 数据库集成测试 | 后端组 | 迁移失败、事务半写、查询口径错误、重试重复 | 数据模型或服务改动 |
| 浏览器 E2E | 测试组 | 导入、分析、查看、处置、导出主流程阻断 | M4 起及发布前 |
| 发布包冒烟 | 工程组+测试组 | 缺运行时、绝对路径、端口/进程、启停和复位错误 | 每个 Windows 发布候选 |
| 人工彩排 | 主智能体+测试组 | 页面可理解性、演示节奏、明显显示和恢复问题 | G6 前两次 |

测试数据只使用仓库合成样例或测试运行时生成的数据。不得接触或模拟为真实公司生产数据。

## 4. 性能与稳定性口径

- P0 只记录目标 Windows 电脑上 `demo` 20,000 行的导入、分析、看板和报告耗时，不预先把某个数字包装成工业指标。
- 100,000/1,000,000 行生成集只用于发现明显退化和建立后续基线；失败不应被描述为违反“千万级”承诺，因为本阶段没有该承诺。
- 稳定性验证覆盖两轮连续彩排、正常重启和一次算法服务失败恢复，不用短测结果外推 7×24 小时。
- M12 在同一候选上增加预热后五轮 300 行闭环和三轮 20,000 行闭环，记录环境、耗时、内存、连接和服务日志；120 秒只是当前审核电脑的演示保护上限，不是工业性能承诺。

## 5. 缺陷等级与发布门槛

| 等级 | 定义 | 发布处理 |
|---|---|---|
| 阻断 | 无法启动/停止/复位，主流程无法继续，数据不可恢复损坏，报告无法打开 | 必须修复并重新执行受影响门槛 |
| 严重 | 关键数字错误、错误地显示成功、处置/审计缺失、明显崩溃或持续报错 | 必须修复并执行针对性回归 |
| 一般 | 有可接受绕行且不影响结果的显示、文案或次要交互问题 | 记录证据和处置决定，可在不影响审核时修复 |
| 建议 | 不影响需求和演示的增强 | 不进入当前阶段，避免范围膨胀 |

修复后只重跑能证明修复和受影响相邻路径的检查；公共契约、迁移或打包改变时才扩大回归范围。

## 6. 验收证据

每次里程碑记录：构建提交、Windows 版本、执行命令、测试结果、样例种子/算法版本、耗时、失败日志位置、未关闭缺陷和最终判定。截图是辅助证据，不能代替自动结果和数据库/API 对账。

M12 固定入口为 `scripts/dev/test.sh`、`powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/native/verify-release.ps1` 和 `python3 tests/reliability/run.py`。依赖审计原文、恢复事实、有限运行摘要和三类服务日志必须随候选保存，不能只记录不可逆哈希或口头结论。

历史文档中的“测试通过”“已结项”和性能数字不得写入当前证据。当前实现只有在对应检查于当前提交上运行后才能标记通过。

M14 自动化只负责生成并验证候选、执行标准用户技术预检、HTTPS 容器闭环、来源矩阵和交付物一致性。AC-022 必须由未参与候选开发的业务人员填写[业务使用手册第 15 节](../guides/business-user-manual.md#15-m14-非技术业务人员终验记录)，并把完整提交、ZIP 路径、SHA-256、环境、逐项结果、缺陷和签名绑定在同一记录中。人工 PASS 后，原始填写内容转存到 `docs/verification/evidence/M14.md`，`automation/state.json` 同时登记结构化绑定；发布校验器要求两者一致。自动化不得代填人工 PASS；人工终验通过也不自动授权 `dev → main` 发布合并。
