# M12 恢复、质量与运行可靠性实施设计

## 1. 目标与边界

M12 从已通过身份、授权和部署边界的 `5f3cce8` 检查点出发，证明正式初版可以恢复、可以安全清理，并在可复现的有限运行中没有明显资源、外联、乱码或 20,000 行退化问题。阶段对应 PRD-002、PRD-003、PRD-005、PRD-019、PRD-022、PRD-024、PRD-034。

本阶段不把短时测试外推为 7×24 小时工业稳定性，不恢复脱离硬件和数据分布的千万级固定响应承诺，也不建设 MSI、Windows 服务、自动更新、异地容灾或通用运维平台。

## 2. 唯一实现路径

### 2.1 隔离恢复

Windows 发布包继续由 `backup.ps1` 生成 PostgreSQL 自定义格式备份。新增恢复验证只接受当前包 `backups` 目录内的普通 `.dump` 文件，并执行以下固定流程：

1. 读取并核验当前发布 manifest、运行配置、包内 PostgreSQL 程序及备份清单。
2. 在当前发布包运行目录内创建唯一临时恢复目录，使用与业务实例不同的可用回环端口启动独立 PostgreSQL。
3. 创建隔离数据库，用 `pg_restore --exit-on-error` 恢复，不停止、不覆盖、不连接为写目标到现有业务数据库。
4. 默认验证 Flyway、关键业务表和序列均可查询，并输出隔离库事实摘要；历史或外来恢复点不要求等于当前业务库。
5. 仅在 M12 紧邻备份且业务静止的验收中启用 `-RequireCurrentMatch`，分别查询源库与隔离库的迁移、行数和稳定内容摘要；源库在验证期间变化或任一摘要不同即失败。
6. 停止隔离实例并只删除本次创建且仍位于精确恢复根下的临时目录；失败日志保留在发布包日志目录。

该流程用于证明备份可恢复，不在业务实例上提供覆盖式“恢复”按钮，避免演示阶段误覆盖当前数据。

恢复点元数据记录来源实例和提交，但来源是追溯事实而非恢复拒绝条件。默认清理保留的恢复点、旧实例恢复点和复制到新安装的恢复点仍可执行状态检查与隔离恢复；自动保留策略只删除当前来源且 SHA-256 校验通过的过期恢复点。

### 2.2 备份运营状态

Windows 原生包提供手动备份、当前用户每日计划任务、默认 14 个恢复点的保留策略、失败日志和完整性状态检查。备份、恢复和清理共用实例级互斥；清理会精确核验并等待本实例计划任务停止，不能与 `pg_dump` 竞态删除数据。

系统管理员页面只读展示数据库容量、恢复点元数据、最近成功时间和运维入口。网页不会同步读取大型备份并冒充完成 SHA-256；完整哈希结论必须来自 `scripts\backup-status.ps1`。

### 2.3 精确实例停止与清理

`stop.ps1` 仍只停止 PID 记录、可执行路径、命令行、工作目录和当前发布根全部相符的进程。新增清理入口必须先成功停止当前实例，再核验三个固定端口无当前实例 owner、PostgreSQL 路径别名指向当前发布根，并只清理可重建的 `data/postgresql`、`logs`、`pids` 和实例密钥。

备份默认保留；只有显式选择并二次确认时才允许删除当前发布根下的 `backups`。脚本不得删除发布根本身、父目录、未知 Junction、其他实例、未知进程或当前根之外的路径。自动验收使用全新解压目录，因此可验证清理后的精确边界，不依赖人工观察。

### 2.4 静态质量与依赖

质量入口复用仓库锁定工具链：

- Java：编译、测试并解析实际生产运行时依赖；
- Python：编译、测试并核对精确锁文件；
- Vue/TypeScript：`vue-tsc --noEmit`、正式构建和测试；
- 通用：`git diff --check`、脚本语法、JSON/锁文件一致性；
- 依赖：对 Maven、Python 和 npm 的实际解析依赖执行已知漏洞审计，网络或漏洞数据库不可用时明确失败，不把“未审计”记为通过。

只修复当前规则发现的真实问题；不进行全仓格式重写，不扫描来源提取物或生成物，不为通过而降低规则。

### 2.5 有限运行可靠性

`tests/reliability/run.py` 复用当前 Java、Python、PostgreSQL 和浏览器/API 业务路径，不复制业务实现：

1. 从干净端口启动开发栈并记录受管进程、端口和初始资源。
2. 完成一次预热，再重复执行合成样例导入、分析、查询和项目内复位；每轮核验相同业务摘要。
3. 记录 Java、Python 和 PostgreSQL 的 RSS。五轮 300 行用于形成预热样本，三轮独立 20,000 行重载用于判断持续显著增长；任一样本超过演示电脑保护上限也会失败。该检查只用于发现明显泄漏趋势，避免把 JVM 正常预热误判为泄漏。
4. 扫描受管进程连接，只允许受支持的回环或容器内部连接；发现无理由公网外联即失败。
5. 扫描 API、页面和服务日志的 UTF-8 替换字符、典型乱码和未处理异常。
6. 运行 20,000 行导入与分析并记录耗时，与同一候选内的重复结果比较；只拒绝明显失败或数量级退化，不声明固定工业性能。
7. 各部署入口将 Java 后端堆限制在 128–768 MiB；这能为 20,000 行演示保留足够工作空间，并防止 JVM 按宿主机总内存无界扩堆。
7. 正常停止后核验 PID 文件、三个固定端口和受管进程均无残留；测试创建的容器、目录和临时密钥均按精确身份清理。

所有阈值、样本、耗时和资源值写入机器可读结果；门槛失败时保留日志并影响下一步，不用固定 sleep 或模拟数据结果制造通过。

## 3. 实施顺序

1. 为恢复、清理和可靠性结果冻结命令、字段、失败语义与路径边界。
2. 实现发布包隔离恢复和精确清理，并将正向及越界负控纳入 Windows 发布验收。
3. 实现质量/依赖入口和可靠性编排器，先运行最小定向检查。
4. 只修复门槛真实触发的阻断或严重缺陷，再运行完整 G12。
5. 在固定、已推送且工作树干净的候选上执行独立对抗复审，保存证据后通过 PR 合入 `dev`，再对合并提交执行远端发布级检查。

## 4. G12 验收

工作流固定命令不降低：

```text
scripts/dev/test.sh
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/native/verify-release.ps1
python3 tests/reliability/run.py
```

三条命令必须在同一固定候选上成功。证据至少记录：恢复前后逐表对账、清理负控、依赖审计结果、重复运行资源样本、实际外联集合、乱码扫描、20,000 行耗时、停止后 PID/端口/容器状态、Windows 双目录结果、失败修复历史和独立复审结论。

达到 G12 只表示当前 Windows 11 目标、固定合成数据和有限运行窗口通过。真实工厂 7×24 小时、任意硬件性能、灾备 RPO/RTO、真实数据算法准确率仍需外部条件和独立阶段，不得写入 M12 通过结论。
