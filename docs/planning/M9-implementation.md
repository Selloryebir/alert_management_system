# M9 可泛化算法模型与解释实施契约

## 1. 目标

以 `hybrid-v2.0.0` 替换固定分数和场景命名耦合：对任意符合数据契约的新报警记录执行可解释时序规则、一阶 Markov 关联发现和可弃权原因分类，并让业务人员在浏览器中调整参数、查看实际参数与版本。

## 2. 最小范围

1. Python 仅对请求做纯计算，不访问数据库、预期文件或合成场景标识。
2. 重复、抖动、短时恢复和持续报警使用显式公式；分数只表示规则强度，不宣称概率或准确率。
3. 关联链按 `site/area/unit` 划分 episode，从跨 episode 的相邻 tag 转移统计中筛选，不根据“步骤”或固定源行识别。
4. 原因分类使用版本化非负专家权重；分数或类别间距不足时返回 `UNKNOWN`。
5. Java 与 Python 的内部契约升级为 `v2`；浏览器业务 API 保持 `/api/v1/**`，历史 v1 运行只读可见。
6. 分析前页面提供 14 个受范围校验的参数；运行完成后显示实际参数只读摘要。
7. 固定 300 行样例改为满足 v2 数学前提的独立金样；20,000 行数据只记录当前机器实测，不外推工业性能。

## 3. 版本与数据边界

- 算法服务：`0.2.0`
- 内部 HTTP 契约：`POST /api/v2/analyze`，`contract_version=v2`
- 规则模型：`hybrid-v2.0.0`
- Java 主系统构件仍为 `0.1.0`；M9 通过后以完整产品标签 `v0.2.0` 发布。
- Flyway V6 只把事件链解释列从 `VARCHAR(500)` 扩为 `TEXT`，不重写既有分析事实。

## 4. 验收 G9

- `scripts/dev/test.sh`：仓库、Java/PostgreSQL、Python、数据金样、契约和前端参数交互全部通过。
- `scripts/dev/m9-algorithm-v2-smoke.sh`：运行时隔离、未见数据、跨 episode Markov、支持不足、随机负控、关系隔离、时间/UUID/顺序变形和确定性通过。
- `scripts/dev/m3-analysis-smoke.sh`：300 行两次完整链路结果一致，算法失联后可重试且零半写，20,000 行经 Java、Python 和 PostgreSQL 完整分析。
- 固定候选必须经独立审查；发现的问题必须在同一阶段修复并重新执行受影响门槛。

项目作用域、图形化字段映射、账号权限、HTTPS、备份恢复、正式说明书和安装器分别由 M10–M14 负责；M9 不创建占位页面或兼容层。
