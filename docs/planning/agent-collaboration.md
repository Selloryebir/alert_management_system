# 智能体协作与责任边界

## 1. 组织方式

采用“主智能体集成 + 专业智能体并行”的方式。专业结构包含算法组、后端组、前端组、工程组和测试组；并发槽不足时工程组与测试组按阶段轮换，不为展示组织结构而复制实现。

| 角色 | 主要所有权 | 不得自行改变 |
|---|---|---|
| 主智能体/技术负责人 | 产品事实、公共契约、阶段门槛、跨模块集成、提交与推送 | 人工确认的范围和对外承诺 |
| 后端组 | Java API、导入、业务状态、数据库迁移、报告、审计 | Python 算法语义、产品状态定义 |
| 算法组 | Python 规则、事件链、算法测试和版本说明 | 数据库、处置状态、对外准确率口径 |
| 前端组 | Vue 页面、交互、可访问错误状态、前端测试 | 后端统计口径和业务状态机 |
| 工程组 | 构建、Windows 包、脚本、配置、日志、Docker | 业务规则和验收数字 |
| 测试组 | 黄金数据、契约/集成/E2E、发布包验收、缺陷证据 | 为使测试通过而修改预期语义 |

## 2. 并行波次

- 波次 A（M0–M1）：主智能体冻结事实和契约；后端、算法、前端分别建立最小健康骨架；工程组建立统一启动。公共文件由主智能体独占。
- 波次 B（M2–M3）：后端负责导入和算法编排；算法组负责规则；前端负责导入/分析壳层；测试组先写样例预期和契约用例。
- 波次 C（M4–M5）：前端和后端完成业务闭环；算法组修复黄金测试差异后转为解释性校验；测试组持续端到端回归；工程组准备原生包。
- 波次 D（M6–M7）：工程组组装发布物；测试组仅在发布物上验收；其他组只修复有复现证据的阻断问题。

## 3. 任务下发格式

每个子任务必须包含：

- 对应 `PRD-*`、所属里程碑和成功标准；
- 允许修改的目录/文件以及公共契约是否只读；
- 至少一个应捕获的具体失败模式；
- 需要回报的命令、结果、残余风险；
- 明确的禁止项，例如不提交、不推送、不做全仓重构。

子智能体完成时只报告证据，不使用“应该可用”。主智能体检查共享工作区、冲突和门槛后统一提交推送。

## 4. 冲突和变更处理

1. 先以数据契约、ADR、需求追踪矩阵的顺序判定；历史材料不能推翻这些基线。
2. 普通内部实现冲突由主智能体选择最小且可验收方案，写入任务或 ADR 后继续，不等待人工。
3. 只有产品事实基线列出的关键情况请求人工介入。
4. 公共契约变更必须同时更新生产者、消费者和契约测试；不能通过兼容双路径拖延收敛。
5. 已通过的阶段不做等价重构。只有明确缺陷、性能证据或后续 P0 阻塞能触发修改。

## 5. 防丢失操作

- 一项可验证增量结束即检查差异并形成提交；阶段门槛通过即推送。
- 提交前查看 `git status`，保留其他智能体的并行改动，不使用破坏性重置或整仓格式化。
- 生成的大样例、构建物和数据库不进入 Git；生成器、种子、预期清单、迁移和构建脚本必须进入 Git。
- 阶段证据记录提交 ID、平台、命令和结论；外部报告不能成为唯一证据副本。
