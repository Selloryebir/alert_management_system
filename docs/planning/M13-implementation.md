# M13 正式说明书与项目过程文件实施约定

## 1. 阶段目标

M13 把 M0–M12 已通过的产品事实、代码入口和验收证据转成业务人员可执行的中文说明书，以及可重复生成的项目过程文件。Markdown 是唯一可编辑事实源，DOCX/PDF 是生成交付物；历史 PDF/DOCX 只提供可追溯候选，不直接提供当前人员、预算、审批或测试结论。

阶段完成不等于业务用户终验或正式发布批准。M14 仍需在 Windows 11 上由不了解源码的使用者按最终说明完成独立验收。

## 2. 最小实施范围

### 2.1 事实源修正

- 根 README 提供 Windows 原生包快速开始和正式手册入口，并使用 `v0.8.0` 及当前自动化状态。
- 文档总入口、产品事实和来源闭环矩阵与 M10–M12 已通过能力一致。
- 历史 57 项来源能力在差距说明中各出现一次，且只有“已实现”“M13”“M14”“外部输入后才可重启”“明确拒绝”五类责任。

### 2.2 正式手册

- 业务使用手册：登录、项目、三格式导入、映射纠错、分析、看板、详情、人工修订、责任人账号、处置、报告和常见错误。
- Windows 部署与运维手册：ZIP 校验、预检、启停、日志、备份、状态检查、计划任务、隔离恢复验证、精确清理，以及 Docker/HTTPS 管理员附录。
- 页面或命令不存在时不得通过说明文字补出假入口；恢复只表述为隔离恢复验证。

### 2.3 项目过程文件

生成立项、中期、测试、技术结项、研发过程和原始方案差距说明。未知公司主体、项目编号、负责人、预算、成本、审批、签章和知识产权状态明确留给项目管理方填写，不继承历史材料中的值。中期报告以 M7 Git 检查点补编；技术结项只说明当前技术范围具备进入 M14 的条件。

### 2.4 生成与随包交付

- `tools/deliverables/build.py` 从登记的 Markdown 生成中文 DOCX/PDF，并验证确定性、结构、文本、字体和主动内容边界。
- `python3 tools/deliverables/build.py --check` 只读重建并与跟踪产物比较，缺失、陈旧、多余或不可解析均失败。
- Windows 原生包携带业务使用和部署运维两份 PDF/DOCX，发布 manifest 对其大小和 SHA-256 负责。

## 3. 协作边界

| 责任 | 所有路径 | 输出 |
|---|---|---|
| 业务与部署说明 | `docs/guides/**` | 两份真实操作手册 |
| 项目与对抗审查 | `docs/deliverables/**` | 六份事实驱动过程文件及 57 项差距响应 |
| 文档工程 | `tools/deliverables/**`、`deliverables/**` | 确定性生成器、锁定依赖、DOCX/PDF 和清单 |
| 控制器 | 共享事实、打包、CI、状态和 Git | 集成、验收、证据、PR 与检查点 |

执行者不提交、不推送、不修改自动化状态。控制器只在实际差异合并后运行门槛并建立固定候选。

## 4. 验收顺序

1. 定向检查 Markdown 链接、57 项唯一性、历史高风险值和责任人账号提示。
2. 执行 `python3 tools/deliverables/build.py --check`，确认两次临时生成字节一致且与跟踪产物一致。
3. 执行 `python3 scripts/validate_repository.py` 和 `python3 scripts/validate_formal_baseline.py`。
4. 执行受影响的前端测试、原生模板/构建检查和 `git diff --check`。
5. 固定候选后由未参与实现的审查者核对手册命令、文档声明、生成物和打包清单；阻断或严重问题为零后才能合入 `dev`。
