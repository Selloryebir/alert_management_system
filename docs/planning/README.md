# 阶段开发计划

## 1. 交付原则

- 目标顺序：能启动 → 闭环可用 → 固定样例可验收 → Windows 原生可交付 → Docker 可选增强 → 正式产品化 → 发布候选。
- 每个功能在同一任务内完成实现、针对性测试和必要说明，不留下“后续补测试/补契约”的占位债务。
- 只处理当前支持路径可到达的异常；不进行无目标的全仓审计、投机性抽象、兼容层或等价重构。
- 阶段门槛未通过时只修复该门槛的失败，不启动依赖它的新阶段。
- “采用”表示授权开发，不表示已经实现；只有证据齐全才能宣称阶段完成。

## 2. 总体里程碑

```text
M0 事实冻结
  -> M1 可运行骨架
  -> M2 数据导入与样例
  -> M3 算法闭环
  -> M4 前端业务闭环
  -> M5 报告与审计
  -> M6 Windows 原生发布
  -> M7 Docker 次级交付
  -> M8 正式产品基线与来源闭环
  -> M9 可泛化算法模型与解释
  -> M10 项目化业务与全中文 UX
  -> M11 身份权限与安全部署边界
  -> M12 恢复、质量与运行可靠性
  -> M13 正式说明书与项目过程文件
  -> M14 Windows 11 业务用户终验与发布候选
```

M0–M7 已形成 `v0.1.0` 可运行基线。M8–M14 的完整范围、人工门禁和版本节点见[产品化蓝图](productization-blueprint.md)；每阶段仍只实现一个可独立验收的增量。

## 3. 阶段与验收门槛

### M0：来源提取与产品事实冻结

步骤：

1. 将四份原始材料按来源拆为 Markdown 和必要图片，记录原文件、页码/章节、提取方式和排除理由。
2. 明确排除 PDF 占位代码和非报警项目材料；保留可追溯索引，不把排除内容复制进产品提示。
3. 使用[需求追踪矩阵](../product/requirements.md)完成采用、调整、延期、拒绝登记。
4. 冻结[数据契约 v1](../product/data-contract.md)、[架构基线](../architecture/README.md)和决策记录。

门槛 G0：每个来源段落有去向；所有 P0 条目均有唯一含义和验收入口；文档链接检查通过；不存在未裁决且会改变 P0 的冲突。

### M1：可运行工程骨架

步骤：

1. 初始化 Java、Python、Vue 和数据库迁移模块，固定依赖和目录职责。
2. 建立 Java、Python 健康端点，Java 验证 PostgreSQL 连接并聚合健康状态。
3. Vue 构建为 Java 静态资源，提供产品标识和服务状态页。
4. 建立统一配置示例、日志关联字段以及开发启动/停止命令。
5. 建立最小 CI/本地检查：编译、单元测试、格式/静态检查和文档链接。

门槛 G1：从干净检出按根 README 启动四组件；浏览器可见重建标识和三项健康状态；重启后数据库迁移不重复失败；所有基础检查通过。

### M2：合成数据与导入闭环

步骤：

1. 先实现固定种子的场景生成器和独立预期清单，再生成 `smoke`、`demo`、`invalid` 数据。
2. 实现 CSV、制表符 TXT、XLSX 的表头预览、字段映射和统一规范化。
3. 实现全文件校验、中文错误摘要、批次状态和事务性落库。
4. 提供批次列表、导入详情和原始行追溯 API；前端先完成最小导入向导。

门槛 G2：三种 300 行等价样例得到相同规范化记录和摘要；非法样例逐项命中预期错误且不产生半批次业务数据；20,000 行 Demo 可在目标电脑导入；自动测试覆盖上述失败模式。

### M3：算法与分析闭环

步骤：

1. 按契约实现 Python 规则分析，规则版本和参数显式记录。
2. 覆盖重复、抖动、短时、持续、工艺扰动、设备故障、仪表问题、维护测试和未知类别。
3. 实现关联事件链的时间窗/关系规则及证据说明。
4. Java 实现调用、超时、契约校验、结果原子保存、失败展示和明确重试。
5. 测试组用独立预期清单建立黄金测试和 Java—Python 契约测试。

门槛 G3：固定种子相同输入重复运行结果一致；所有声明场景的预期检查通过；算法不可用和非法响应时任务明确失败且无部分结果；界面/日志不出现“已证明根因”或真实准确率措辞。

### M4：前端业务闭环

步骤：

1. 完成总览、趋势、优先级/装置/类别分布及筛选。
2. 完成报警列表、详情、原始行、规则证据和关联事件链展示。
3. 完成 `OPEN → IN_PROGRESS → CLOSED` 处置及必要退回。
4. 对空数据、校验失败、算法失败和服务不可用提供明确中文状态。
5. 建立浏览器端到端测试覆盖导入、分析、查看和处置主路径。

门槛 G4：审核员仅通过浏览器可完成 20,000 行 Demo 的主流程；看板固定抽样与数据库查询一致；关闭操作保存操作者、时间和说明；P0 端到端测试通过。

### M5：报告、审计和演示复位

步骤：

1. 生成带产品名称和合成数据标识的 PDF/XLSX 报告。
2. 实现导入、分析、人工修订、处置、导出审计事件查询。
3. 实现仅针对本地 Demo 实例的备份和一键复位。
4. 固化演示步骤、预期截图/数字和失败恢复说明。

门槛 G5：报告可由常用阅读器打开且关键数字与界面/数据库一致；关键动作审计字段完整；复位两次后初始数据和演示结果一致；复位不影响项目目录外数据。

### M6：Windows 11 x64 原生发布与验收

步骤：

1. 构建自包含 Java 运行时、Python 算法可执行文件、PostgreSQL 本地运行时和应用资源。
2. 完成 `preflight`、`start`、`stop`、`reset-demo`、`backup` PowerShell 脚本。
3. 在当前 Windows 11 x64 电脑以发布包而非开发进程执行安装前预检和全流程。
4. 从新解压目录再执行一次，确认无隐含绝对路径和开发工具依赖。
5. 记录版本、构建提交、测试结果、已知非阻断限制和演示手册。

门槛 G6：无预装 JDK/Python/Node 的运行路径成立；启动脚本等待健康后才返回成功；两轮完整彩排均通过；P0 测试全绿；阻断/严重缺陷为零。只有达到 G6 才可称“原生 Demo 可交付”。

### M7：Docker Compose 次级交付

步骤：

1. 容器化相同 Java/Python 构件和 PostgreSQL 主版本，复用迁移、配置语义和样例。
2. 建立 Compose 启动、停止、健康和项目专用数据卷复位命令。
3. 对 Compose 运行相同的 API/端到端冒烟测试。

门槛 G7：Compose 从空卷健康启动并通过关键冒烟；与原生包的固定样例摘要一致；不引入第二套业务实现。

### M8–M14：正式产品化

- M8 冻结正式产品身份、来源能力处置、算法/安全基线和自动化阶段；详见 [M8 实施契约](M8-implementation.md)。
- M9 以数学化专家规则、一阶 Markov 关联和可弃权分类替代与合成命名耦合的算法路径。
- M10 提供项目数据作用域、可视化字段映射、中文枚举和首次使用引导。
- M11 提供登录授权、项目级访问边界、HTTPS 网络部署及输入资源限制。
- M12 提供可验证恢复、安全安装卸载、资源/性能观察和集中代码质量门槛。
- M13 从 Markdown 事实源生成正式 README、业务手册和项目过程 DOCX/PDF；详见 [M13 实施约定](M13-implementation.md)。
- M14 在 Windows 11 上按非技术业务用户场景完成最终彩排和发布候选审查。

每个阶段的精确标准和命令以 `automation/workflow.json` 为唯一机器入口；M14 通过不自动授权 `v1.0.0` 或 `main` 正式发布。

## 4. 阶段提交与推送策略

- 主智能体在每个门槛通过后创建一个可回滚的阶段提交并立即推送远端当前工作分支；并行子智能体不自行提交共享分支。
- 门槛内允许按独立可验证增量增加小提交，但不得提交不可编译的半成品或空占位模块。
- 推送前只运行会影响本次结论的检查：受影响模块单测、契约/集成检查、文档链接和 `git diff --check`。不重复已经由同一提交状态证明通过的检查。
- 提交信息说明里程碑和对应 `PRD-*`；验收证据记录构建提交，避免代码与报告错配。
- 发现外部存储异常时，优先停止新增改动，确认本地提交对象和远端提交可见，再继续；不以未推送工作区作为唯一副本。

## 5. 完成定义

任何功能完成必须同时具备：

1. 实际可达的用户路径；
2. 与冻结契约一致的实现；
3. 能捕获其主要失败模式的测试；
4. 错误路径不给出假成功；
5. 用户可理解的最小说明；
6. 不含 `TODO` 页面、假数据占位接口、未消费抽象或“稍后实现”的运行分支。

“当前未发现明显 bug”只能基于[测试与验收策略](../verification/README.md)所列证据表述，不等于不存在所有缺陷。
