# Git 分支与远端保全流程

## 1. 目的与边界

本流程服务于快速、可回退的 Demo 重建，只规定 `main`、`dev`、`feat/*`、`hotfix/*` 四类真实分支及其生命周期。阶段内容和门槛以[阶段开发计划](../planning/README.md)为准，智能体职责以[协作边界](../planning/agent-collaboration.md)为准；本文不重复功能计划或测试清单。

核心原则是：可验证增量及时形成 Git 对象并推送远端，远端可见后才视为已有异机副本；不以未提交工作区、构建目录或聊天记录作为唯一恢复来源。

## 2. 分支职责

| 分支 | 来源 | 用途 | 允许合入目标 | 直接提交规则 |
| --- | --- | --- | --- | --- |
| `main` | 仓库基线 | 已通过发布门槛的可交付版本 | - | 禁止日常直接提交；仅通过 `dev` 发布合并或 `hotfix/*` 紧急合并更新 |
| `dev` | `main` | 下一阶段的稳定集成线 | `main` | 禁止功能开发直接提交；只接收已复核的 `feat/*`、已发布热修同步、必要的集成冲突修复及合并后的阶段证据/状态迁移 |
| `feat/<scope>` | 最新 `origin/dev` | 一个边界明确、可验证的功能或治理增量 | `dev` | 由主智能体在检查共享差异后统一提交 |
| `hotfix/<scope>` | 最新 `origin/main` | 修复当前可交付版本中的阻断或严重问题 | `main`，随后同步 `dev` | 与功能分支相同，但验证必须覆盖线上/发布包复现路径 |

一个分支只承载一个可说明的目标。不得为并行展示长期保留空分支，也不得把互不相关的修复塞入同一功能分支。

## 3. 功能分支生命周期

1. **开始**：主智能体确认工作区中不存在会被覆盖的其他智能体改动，执行 `git fetch --prune origin`，从最新 `origin/dev` 创建 `feat/<scope>`。开始前记录基线提交。
2. **协作**：子智能体按任务限定路径修改共享工作区，只回报差异、命令、结果和风险；**子智能体不得自行提交、推送、合并、变基或删除共享分支**。公共契约及跨组冲突由主智能体处理。
3. **提交**：主智能体审阅实际 diff，确认没有混入其他任务，运行与本增量有关的检查。一个提交必须是可理解、可构建或可独立验证的增量；不提交空占位、已知不可运行半成品或无关格式化。
4. **推送**：首个有效提交即设置上游并推送；此后每个已验证检查点及时推送。推送成功后比较本地 `HEAD` 与远端分支 SHA；二者一致才记录为“远端已保全”。
5. **复核与合并**：按[自动化审计指南](../verification/automation-audit.md)完成独立复核，必要 CI 和受影响门槛通过后合入 `dev`。有可用的代码审查服务时使用 PR；否则由主智能体在本地复核后创建非快进合并提交并推送。两种路径都必须保留真实提交，避免在已推送分支上重写恢复点。
6. **删除**：确认 `origin/dev` 已包含合并结果、阶段证据已推送且没有仍依赖该分支的复核后，先删除远端功能分支，再删除本地分支。删除分支不删除已合入的提交历史。

`dev` 达到某一发布门槛时，由主智能体固定候选提交和证据，通过 PR 合入 `main`。合并完成后在 `main` 上重新核对目标提交和必要发布冒烟；只有[测试与阶段验收策略](../verification/README.md)允许的证据齐全，才能创建对应发布标记或交付包。

## 4. 热修生命周期

1. 从最新 `origin/main` 创建 `hotfix/<scope>`，先保存缺陷复现证据和受影响发布版本。
2. 只实施恢复主流程所需的最小修复，并执行缺陷针对性测试、相邻主路径回归和发布包冒烟。
3. 推送分支并独立复核后，通过 PR 合入 `main`；不得直接覆盖 `main` 或强推。
4. `main` 验证通过后，立即把该合并结果同步到 `dev` 并解决冲突，防止后续发布重新引入缺陷。
5. 只有 `main` 和 `dev` 都包含修复、证据已推送后，才删除远端和本地热修分支。

若修复需要改变 P0 含义、数据契约或对外承诺，它不再是普通热修，必须按[产品事实层的人工介入规则](../product/README.md#6-何时必须人工介入)裁决后继续。

## 5. 提交、推送与远端核验

- 提交信息使用“类型/阶段 + 明确结果”，正文列出关联 `PRD-*`、门槛或缺陷编号；不得写“全部完成”而没有对应证据。
- 提交前至少检查 `git status --short`、目标路径 diff、相关测试和 `git diff --check`。检查范围由变更风险决定，不重复运行与结论无关的全仓审计。
- 推送后使用远端引用核验分支 SHA；网页截图、终端中的“push 完成”文字或本地远端跟踪引用不能单独证明远端已收到对象。
- 阶段证据记录被测试的提交 SHA；证据文档后续提交时，同时记录证据提交 SHA，避免把“文档提交”误认为“被测代码提交”。
- 发布候选合入 `main` 后可创建有说明的发布标签，并将标签推送远端；标签只能指向实际通过发布门槛的 `main` 提交，不预先占位。

## 6. 回退与异常恢复

- 未提交错误由主智能体只撤销自己确认拥有的行；共享工作区中禁止整仓 `reset --hard`、`checkout -- .`、`clean -fd` 或覆盖式格式化。
- 已提交变更使用新的 `git revert` 提交回退。已推送或已合并历史不得通过变基、修改提交或强推重写。
- 未合并功能发生问题时，在原功能分支修复或回退并重新复核；已合入 `dev` 的问题在新 `feat/*` 修复；已进入 `main` 的阻断/严重问题走 `hotfix/*`。
- 涉及数据库迁移或持久数据的回退优先采用前向修复，不假定代码回退能安全逆转数据；具体恢复必须由相应阶段测试证明。
- 发现本机或存储异常时立即停止新增改动，核对最近本地提交、`origin` 分支和发布标签。最后一个经远端 SHA 核验的提交是恢复基线；未核验的本地对象不得宣称已保全。
- 若远端不可用，保留本地提交并停止删除分支；远端恢复后先推送和核验，再继续开发。不得用伪造 SHA、仅存在于日志中的补丁或未验证构建物替代 Git 远端副本。

## 7. 合并与删除门槛

满足以下条件才可合并：目标明确且 diff 已审阅；相关自动检查通过；独立复核结论存在；阻断/严重缺陷为零；需要人工裁决的事项已有明确记录。普通 `feat/* → dev` 不额外等待人工；`dev → main` 若代表向审核方或其他外部对象发布，则必须取得人工发布确认。

满足以下条件才可删除分支：合并提交在目标远端分支可见；证据记录已推送；没有未迁移的修复；不存在依赖该分支的发布包或复核任务。未满足时保留分支，不以“界面显示已合并”代替提交可达性检查。
