# 阶段执行状态机

## 1. 状态模型

状态机同时约束“一个里程碑”和其内部的最小增量。一个里程碑只有在远端检查点确认后才完成；测试通过但尚未提交/推送属于中间状态，不能解锁下一阶段。

```text
LOCKED
  | 前一阶段 COMPLETED
  v
READY -> IMPLEMENTING -> VERIFYING -> GATE_PASSED -> CHECKPOINTING -> COMPLETED
                        |                  |
                        v                  v
                     REPAIRING <----------+
                        |
                        +----> VERIFYING

任一活动状态 --命中人工边界--> AWAITING_HUMAN --明确裁决--> READY/IMPLEMENTING
任一活动状态 --外部环境不可用--> BLOCKED_EXTERNAL --环境恢复--> 原状态
```

M0 没有前置里程碑，在产品事实和来源文件可读时由 `LOCKED` 进入 `READY`。M7 完成后不自动创建 M8；当前蓝图结束。

## 2. 状态定义

| 状态 | 含义 | 允许动作 | 禁止动作 |
|---|---|---|---|
| `LOCKED` | 前置门槛或人工裁决未满足 | 读取事实、检查前置证据 | 实现本阶段功能 |
| `READY` | 前置完成，范围和验收条件明确 | 选择一个最小增量、检查目录所有权、分派任务 | 在没有成功标准时编码 |
| `IMPLEMENTING` | 正在完成当前阶段的最小增量 | 修改允许目录、增加对应测试和说明 | 预做后续阶段、无关清理、公共契约静默漂移 |
| `VERIFYING` | 工作区已具备待验证增量 | 运行受影响检查和当前门槛、保存原始结果 | 一边改代码一边继续沿用旧测试结果 |
| `REPAIRING` | 当前检查已有可复现失败 | 只修复失败原因和必要相邻路径、做针对性回归 | 降低断言、删除失败样例、扩大功能范围 |
| `GATE_PASSED` | 当前阶段所有门槛在同一候选状态通过 | 汇总证据、检查差异和残余缺陷 | 宣称已经远端保存或解锁下一阶段 |
| `CHECKPOINTING` | 正在建立可恢复 Git 检查点 | 主智能体提交、推送、核验远端提交 | 子智能体并行提交、破坏性重写历史 |
| `COMPLETED` | 门槛证据与远端检查点均成立 | 解锁下一阶段、发布阶段结论 | 继续向本阶段追加未规划功能 |
| `AWAITING_HUMAN` | 触及产品、工业、合规、外部发布或不可恢复操作边界 | 汇总选项、影响和推荐，等待明确裁决 | 猜测授权、先实施后补批 |
| `BLOCKED_EXTERNAL` | 缺少环境、凭据、许可证、磁盘或外部服务 | 保留工作区、只读诊断、验证恢复条件 | 用假实现绕过依赖或宣称通过 |

## 3. 合法迁移与证据条件

| 从 | 到 | 触发条件 | 必需记录 |
|---|---|---|---|
| `LOCKED` | `READY` | 前置阶段为 `COMPLETED`，或 M0 初始条件成立 | 前置检查点、当前基线提交 |
| `READY` | `IMPLEMENTING` | 任务含需求、范围、失败模式和验收命令 | 任务摘要、允许路径 |
| `IMPLEMENTING` | `VERIFYING` | 实现与对应测试完成，差异未越界 | 变更文件、预期检查 |
| `VERIFYING` | `REPAIRING` | 一个具体检查失败且可在仓库范围修复 | 失败命令、退出码、最小复现、日志位置 |
| `REPAIRING` | `VERIFYING` | 已实施针对性修复 | 修复原因、受影响检查；尝试次数加一 |
| `VERIFYING` | `GATE_PASSED` | 当前门槛全部通过，阻断/严重缺陷为零 | 命令、结果、环境、数据/算法版本 |
| `GATE_PASSED` | `REPAIRING` | 差异复核发现越界、证据缺失或新严重缺陷 | 失效证据和需要重验的范围 |
| `GATE_PASSED` | `CHECKPOINTING` | 证据完整，只有预期文件变更 | 差异摘要、拟提交阶段和需求 |
| `CHECKPOINTING` | `COMPLETED` | 提交成功、推送成功、远端提交可解析且指向已验收内容 | 本地/远端提交 ID、分支、推送结果 |
| `CHECKPOINTING` | `REPAIRING` | 提交检查、推送或远端核验失败且仓库内可修复 | 失败输出、仓库状态、恢复动作 |
| 任一活动状态 | `AWAITING_HUMAN` | 命中人工门禁 | 已知事实、选项、推荐、未执行动作 |
| `AWAITING_HUMAN` | `READY` | 人工改变范围或要求重选任务 | 明确答复、更新后的产品事实/ADR |
| `AWAITING_HUMAN` | `IMPLEMENTING` | 人工授权当前任务按原范围继续 | 明确答复和授权边界 |
| 任一活动状态 | `BLOCKED_EXTERNAL` | 仓库内修改无法解除外部条件 | 外部条件、最近成功状态、恢复判据 |
| `BLOCKED_EXTERNAL` | 原状态 | 外部条件已实际恢复并通过一次针对性检查 | 恢复证据和回归入口 |

除此之外的迁移均非法。尤其禁止 `VERIFYING → COMPLETED`、`REPAIRING → CHECKPOINTING`、`LOCKED → IMPLEMENTING` 和“测试失败但记录为一般缺陷后继续”。

## 4. 阶段状态记录

持久化文件使用小写状态，映射关系见根目录的[自动化阶段控制](../../automation/README.md)。`READY` 尚未选择最小增量时，`active_run` 为 `null`，恢复时从最新 `origin/dev` 重新选择；从 `READY` 进入实现后，每次迁移都在 `active_run` 保存以下字段，使中断后能从 Git 和证据恢复，而不是依赖会话记忆：

| 字段 | 内容 |
|---|---|
| `milestone` | `M0` 至 `M7` |
| `gate` | 对应 `G0` 至 `G7` |
| `state` | 本文定义的状态 |
| `base_commit` | 开始该增量时的提交 |
| `requirements` | 受影响 `PRD-*` 列表 |
| `allowed_paths` | 本增量允许修改的路径 |
| `attempt` | 针对当前同一失败的修复次数 |
| `checks` | 命令、退出码、运行时间和证据位置 |
| `failures` | 稳定复现、影响范围和最近诊断；无失败时为空列表 |
| `decision` | 通过、修复、外部阻塞或请求人工的依据 |
| `checkpoint_commit` | 仅在提交后填写 |
| `remote_verified` | 仅在远端可解析同一提交后为真 |
| `next_action` | 唯一下一动作，不保存模糊任务列表 |
| `resume_status` | 仅暂停时保存恢复前的小写活动状态，其他状态为 `null` |

每阶段的 `attempt`、证据文件、检查点提交、远端核验和下一动作保存在 `stages` 条目；当前增量的其余字段保存在 `active_run`。阶段证据必须随检查点提交进入远端。运行日志和大构建物可以保存在发布物目录，但状态记录必须包含稳定的相对位置和能判定结果的摘要。

## 5. 失败处理算法

1. 在 `VERIFYING` 固定失败命令、输入、退出码和第一处有效错误，不同时追逐后续连锁报错。
2. 判断失败是否由本阶段允许范围内的代码、契约、样例或脚本导致。
3. 若是，进入 `REPAIRING`，只修改能够解释该失败的最小文件集合；修复后先重跑原失败检查。
4. 原检查通过后，只补跑受改动影响的相邻检查，再返回阶段门槛；不得无条件全量重跑。
5. 同一失败两次针对性修复仍没有新证据时，停止重复修改，做一次隔离诊断：缩小输入、核对环境、比较最近成功提交或由独立测试角色复现。
6. 隔离诊断证明是外部条件则进入 `BLOCKED_EXTERNAL`；证明触及产品决策则进入 `AWAITING_HUMAN`；否则保留在 `REPAIRING`，但下一动作必须来自新证据。

不得通过捕获异常后返回成功、删除失败断言、放宽固定预期、写死演示结果或跳过服务健康来解除失败。

## 6. 并行任务的状态约束

- 主里程碑处于 `IMPLEMENTING` 时可以创建多个目录互斥的子任务；每个子任务独立经历“实现—局部验证—回报”，但不能自行将主里程碑推进到 `GATE_PASSED`。
- 公共契约、数据库迁移顺序、根构建文件和验收预期同一时间只能有一个所有者。
- 子任务失败只暂停依赖它的分支；其他不依赖任务可以继续，但不得越过主阶段边界。
- 集成后任何一项阶段检查失败，主状态统一进入 `REPAIRING`；不能用“多数子任务成功”抵消失败。
- 用户插入的新请求若只是当前目标补充，纳入当前状态；若替换目标，先保存现状和证据，再由主智能体重新判定阶段，不能同时推进两套北极星。

## 7. 检查点与恢复

- 检查点只包含当前阶段允许的完整增量和证据，不混入构建物、大型生成数据或其他智能体的无关修改。
- 推送失败时保留本地提交，记录失败并恢复远端连接；不反复重写相同提交，也不强制推送。
- 平台或会话中断后，先读取最近远端检查点和状态记录，再查看本地工作区。若存在未提交差异，将其视为未验证候选，不根据聊天记忆宣称完成。
- 远端检查点存在且工作树仅有后续明确增量时，从记录的 `next_action` 恢复；证据无法对应提交时退回 `VERIFYING`。
- 已完成阶段出现新问题时，只有可复现且影响 P0/后续门槛的缺陷才重新打开；一般增强进入延期清单，不触发等价重构。

## 8. 蓝图终态

- M6 `COMPLETED`：允许表述“Windows 11 x64 原生 Demo 已按当前 P0 验收”，不得外推工业性能、合规或真实准确率。
- M7 `COMPLETED`：允许表述“Docker 次级启动方式通过同源冒烟”，不得称为生产级容器平台。
- 对外提交审核材料、接入真实系统或改变产品承诺仍需单独人工授权；技术阶段完成不会隐式授予这些权限。
